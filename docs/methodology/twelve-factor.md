# The twelve-factor methodology

The [twelve-factor](https://12factor.net) app methodology was written for
network services with backing stores and horizontal scaling. The target
pure-analyzer product is a CLI tool plus a future per-editor-session LSP server
over stdio — it
has no database, no queue, no HTTP/gRPC surface, and nothing to horizontally
scale. Rather than force-fit factors that don't apply, this page states plainly,
per factor, what actually transfers and what's honestly not applicable — that's
more useful than a checklist that lies. It grows through reviewer-approved PRs
as the CLI, LSP server, and any real config surface land. This page is
analyzer-specific; PureCARD's product-local forwarding page does not inherit
these CLI/LSP contracts.

| #    | Factor                                                         | What it means here                                                                                                                                                                                                                                                                                                                                           | Enforced by                               |
| ---- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------- |
| I    | **Codebase** — one codebase, many deploys                      | One git repo; one change → one worktree → one PR. "Many deploys" means every versioned tag or binary build comes from the same tree; no workspace package is currently published to crates.io.                                                                                                                                                               | constitution §2                           |
| II   | **Dependencies** — explicit and isolated                       | `Cargo.toml` + `Cargo.lock` (committed, since this ships a binary); every pin is latest-stable-verified and vetted                                                                                                                                                                                                                                           | constitution §2/§4, `cargo deny`          |
| III  | **Config** — in the environment                                | **Adapted, not literal.** A CLI tool's config is primarily flags + `.pure-analyzer.toml` discovery (design doc §6.5, nearest-wins), not env vars — that's the natural interface for a tool invoked per-run rather than a long-lived deployed process. `--print-config` is the one source of truth for what's actually in effect.                             | design doc §6.5                           |
| IV   | **Backing services** — attached resources                      | **Not applicable.** No database, queue, or object store. The `--model` input (PMCD JSON / Pure model file) is a read-only file argument, not an attached service — it's versioned and passed explicitly, never implicitly bound.                                                                                                                             | n/a                                       |
| V    | **Build, release, run** — strict separation                    | Build → verified artifacts → versioned GitHub tag/release → run; nothing is configured into the binary at build time. crates.io publishing remains disabled until a package has a supported public API.                                                                                                                                                      | the release pipeline (release-plz)        |
| VI   | **Processes** — stateless, share-nothing                       | The CLI is trivially stateless — one invocation, one exit. The LSP (v0.2) holds in-memory analysis state, but scoped to one editor session/process, never shared across processes — there is no cross-process shared state to worry about either way.                                                                                                        | n/a beyond the process boundary itself    |
| VII  | **Port binding** — export services via port binding            | **Not applicable to the CLI.** The LSP (v0.2) communicates over stdio using the LSP JSON-RPC protocol (`tower-lsp`), not a self-owned network port — the editor spawns and owns the process.                                                                                                                                                                 | design doc §1.5                           |
| VIII | **Concurrency** — scale out via the process model              | **Adapted.** Concurrency is intra-process data parallelism (`rayon`, design doc §3) across input files in one invocation, not horizontal process scaling — there's no request load to scale against.                                                                                                                                                         | `rayon` (workspace dependency)            |
| IX   | **Disposability** — fast startup, graceful shutdown            | CLI: fast start, exits the moment work is done, nothing to drain. LSP (v0.2): must shut down cleanly on the client's `exit` notification, losing no in-flight diagnostic.                                                                                                                                                                                    | n/a today; LSP shutdown handler in v0.2   |
| X    | **Dev/prod parity** — keep environments similar                | **Adapted.** There's no separate "prod" deployment to drift from dev — the same binary runs locally, in CI, and in the editor. Parity instead means tests exercise the *real* parser/resolver against real `.pure` fixtures and real models (design doc §8), never mocking the engine.                                                                       | `tests/corpus/`, `tests/golden/`          |
| XI   | **Logs** — treat as event streams                              | **Adapted, deliberately not "stdout only."** Structured `tracing` goes to **stderr**, never a log file, never `println!` — stdout is reserved for the tool's actual output (diagnostics in `--format human`/`json`, LSP JSON-RPC frames), so logs must never contaminate it. Getting this backwards would corrupt the primary interface, not just be untidy. | constitution §1                           |
| XII  | **Admin processes** — run one-off admin as one-off processes   | One-off admin/dev tasks are `cargo xtask` subcommands and `just` targets, not endpoints                                                                                                                                                                                                                                                                      | `xtask`, `just` targets                   |

## Config, specifically

Factor III's usual "one struct, env-var-driven, generated reference" machinery
is still the right pattern *if and when* pure-analyzer grows settings dense
enough to need one — the CLI flags + `.pure-analyzer.toml` discovery (design doc
§6.5) already gives `--print-config` as the single source of truth for what's in
effect, which is the load-bearing property this factor is actually protecting
(no setting takes effect without being visible in one place). If the config
surface grows past what flags/a config file can hand-document, revisit this
section with the same "a figure a doc cites must be machine-asserted against its
source, not hand-copied" principle the lessons ledger records elsewhere.
